## 0.0 范围基线（2026-10-06 用户确认，**优先级最高，覆盖本文档其他一切表述**）

### 产品定位

**面向个人的单用户程序**，不是团队协作工具。

### 实际运行情况（只有两种）

| # | 形态 | 面板 | Agent |
|---|---|---|---|
| **1** | 面板在本地 Windows，Agent 在目标 MC 服务器 | 本地 `127.0.0.1` | 远程主机 |
| **2** | 面板与 Agent 都在 MC 服务器主机上 | 同机 | 同机 |

两种形态下面板都**可能通过反向代理或直接端口对外访问**。

### 主职责

**创建与托管服务器**。这是产品的核心，一切功能优先级以它为准。

### 明确的能力边界

| 能力 | 判定 | 说明 |
|---|---|---|
| 玩家背包 / 物品操作 | ❌ **不由面板实现** | 必须由 mod/插件完成——面板没有游戏内 API。**但后续可考虑「用面板安装插件 + 操作插件配置」来间接达成** |
| 游戏地图渲染 | 🅿️ **有需求，非当前可实现** | 保留为独立里程碑（P4-1），不在近期排期 |
| 多用户 / RBAC / API Token / SSO / MFA / 审计日志 | ❌ **不做** | 单用户程序，整套用户体系无意义 |

### 由范围确认带来的路线图调整

| 调整 | 影响的工作项 |
|---|---|
| **反向代理是正式支持场景**（形态 2） | **P0-1（`trust proxy`）优先级由「中」升为「最高」**——它就是为这个场景存在的。同时 `Secure` Cookie（P0-2）在反代 HTTPS 下同样必需 |
| 多用户体系整体砍掉 | 原附录 A.1 中被标记「暂不排期」的多用户/RBAC/API Token/SSO/MFA/审计日志 → **正式移出范围，不再列为缺口** |
| **i18n 与错误码表提级** | 用户明确要求「中英双语 + 错误反馈设计错误代码表」。原 P3-3（i18n）与 P1-2（错误契约）→ **合并为 P1 阶段的核心工作**，见下方新增的 §P1-8 / §P1-9 |
| 插件安装 + 配置成为扩展能力的**路径** | 原 P4-3（扩展系统）→ 降级；改为强化「插件/Mod 安装与管理 + 配置可视化」这条既有链路（`web/src/lib/plugin-config.ts` 已存在，是资产不是负债） |
| NBT / 背包编辑 | 明确**不做**（架构不可行）。原 P4-2 仅保留「只读 NBT（如 `level.dat` 展示）」作为可选小项，物品编辑彻底移除 |
| 皮肤 / 白名单 / OP | 保留（P4-4 / P4-5），成本低且服务于「托管服务器」主职责 |

### 两条工程约束（用户明确要求）

1. **不重复造轮子**——优先复用仓库已有设施：`emitter`/SSE 事件总线、`agent/` 的零依赖测试 harness（`check()`/`report()` 模式）、shadcn/Tailwind、既有的 `web/src/lib/plugin-config.ts`（447 行，含 YAML 注释保留与自动降级）、`web/src/lib/properties.ts`（62 键无损回写）。**新增能力前先 grep 确认没有现成实现。**
2. **耦合尽可能地低**——每个改动独立可回滚；不引入全局单例式的隐式依赖；错误码表与 i18n 都做成「可独立替换的数据层 + 极薄的调用点」，而不是把文案逻辑渗进业务代码。

## 0. 路线图总览

### 0.1 现状一句话

BlockNexus 的**传输安全、存储原子性、上传可靠性**已经领先 OPanel（见 adoption-plan §4）。真正的短板集中在五处：**前端工程质量（零测试、零 i18n、零类型契约）**、**实时通道只有单向**、**调度只有 30 秒轮询**、**指标无历史**、**MC 领域理解止步于配置文件**。

**合计 33 个工作项**（原 33 项经范围调整后：`+P1-8 错误码表`、`+P1-9 双语`、`−P3-3 原 i18n 条目（并入 P1-9）`）。

## P1-1 类型化设置仓库（localStorage）

| 项 | 内容 |
|---|---|
| **问题** | 设置散落在组件里，无统一入口。例：控制台 `MAX_LINES = 1500` 是模块常量（`web/src/components/console-panel.tsx:11`）、终端高度是 props 默认值（`:56`）、日志级别是硬编码中文映射（`:203`）。改一个默认值要改组件源码并重新构建 |
| **收益** | 用户可以调终端行数/字号/级别过滤；新增设置零迁移代码；拼错键名编译报错 |
| **参照** | OPanel `lib/settings.ts`（adoption-plan §2.6） |
| **做法** | ① 建 `web/src/lib/settings.ts`：联合类型作 schema（键名 `.` 命名空间）、值类型就是真实类型、`getSettings`/`changeSettings` 泛型绑定；② `state.*` 前缀存界面瞬时状态（上次 tab、指令历史、终端高度）；③ **读时合并**：遍历 defaults 补齐缺失键并写回，未知键保留，整个函数永不抛；④ **必须加模块级缓存**（OPanel 原实现每次 `getSettings` 都全量 `JSON.parse` + `setItem`，在渲染期高频调用，是它唯一的性能隐患）；⑤ 可选：加 `settings-changed` 事件（BlockNexus 已有 SSE，成本极低） |
| **依赖** | 无 |
| **成本** | 1 天 |
| **风险** | 低。纯前端新增，不动后端 |
| **验收** | ① 控制台行数/字号/级别可配置并持久化；② 改默认值只需改 `defaultSettings` 一处；③ 新增设置后老用户首次打开自动补默认值；④ `tsc` 对错误键名报错 |

## P1-2 统一 API 类型契约与错误模型

| 项 | 内容 |
|---|---|
| **问题** | ① **前端手写 TS union，后端 `bus.emit('broadcast', {...})` 是无类型裸对象**（`web/src/lib/sse.ts:3-38` vs `panel/api.js:117`）——改一个事件字段编译器不告诉你前端有 12 处读它；② **响应无统一信封**：成功响应有些返回裸载荷、有些返回 `{ok:true}`，前端 `api<T>()` 因此只检查 HTTP 状态码（`web/src/lib/api.ts:565-585`）；③ 错误文案是中文裸字符串硬编码在后端（`panel/api.js:564` `'未登录'`、`:741` `'服务器不存在'`） |
| **收益** | 契约变更变成编译错误而不是运行时静默错乱；为 P2-1（WebSocket）和 P3-3（i18n）铺路 |
| **参照** | OPanel `lib/types.ts`（路由写进 JSDoc、`APIResponse<T>` 交叉类型）、`api.ts` 的 `toastError` 两层文案模型（adoption-plan §2.2） |
| **做法** | ① 建 `web/src/lib/types.ts`：每个后端路由一个 interface + **路由写进 JSDoc**；② 引入统一错误形状（建议 `{error: string, code?: string}`，**给信封字段加保留前缀避免与业务字段撞名**）；③ 后端把业务错误改成**错误码 + 参数**（如 `{code:'instance.invalid_name'}`）而不是裸中文，前端负责渲文案——**这一步是 P3-3 i18n 的前置**，也可以只做一半（先引入 code，文案暂时仍用中文兜底）；④ `toastError(e, message, [[status, desc]])` 两层文案 + 401 全局跳转 |
| **依赖** | 无（但 P2-1 依赖它） |
| **成本** | 1.5 天 |
| **风险** | 中。改后端错误响应形状会碰到所有前端 catch 点，**必须一次改完**，建议用 `grep -c "errText\|error"` 先清点影响面 |
| **验收** | ① `tsc` 能拦住事件字段改名；② 前端不再有 `api<T>()` 的裸断言；③ 错误响应统一为同一形状，前端单点渲染 |

## P1-4 前端 lint 规则收紧（利用已有 `oxlint`）

| 项 | 内容 |
|---|---|
| **问题** | `web/.oxlintrc.json` 只有 3 条规则。而 OPanel 的教训明确：`typescript/no-explicit-any: off` 与 `react/exhaustive-deps: warn` + 就地 `oxlint-disable` 正是「类型退化」与「依赖漏项」两类 bug 从编译期可见变成运行时偶发的**直接原因** |
| **收益** | 低成本把两类高频 bug 挡在编译期 |
| **做法** | ① `react/exhaustive-deps` 提到 **error**（至少对 `web/src/lib/hooks/**` 与实例相关组件）；② 开启 `typescript/no-explicit-any`，**并把新增的 WS/SSE 层作为第一批整改对象**；③ 补 `import/order` 与风格规则统一全仓视觉（OPanel 用 `@stylistic` 定义 `if(` 无空格、单行早返回，成本低收益高）；④ `components/ui/**` 加入 `ignorePatterns`（shadcn 生成物） |
| **依赖** | 无 |
| **成本** | 0.5 天 |
| **风险** | 中。开启新规则会产生一批既有告警，需分批修（建议先 `warn` 观察一周，再提到 `error`） |
| **验收** | `npx oxlint` 在 CI 中通过且规则已达 error 级 |

## P1-5 § 格式化码富文本渲染

| 项 | 内容 |
|---|---|
| **问题** | **MOTD 当前按纯文本显示，`§` 颜色码不生效**。而 console 已经手写了日志级别着色（`web/src/components/console-panel.tsx:24-39`），基础设施其实已在 |
| **收益** | 立刻改善现有 UI；为 P4 的物品/聊天渲染打基础 |
| **参照** | OPanel `lib/formatting-codes/text.ts`（adoption-plan §3.1(a)） |
| **做法** | ① **跨迭代状态机而非正则**——`currentNode` 游标让「颜色码重置到 root、格式码在颜色层内嵌套」自然成立（正则做不到正确嵌套语义）；② `§x§R§R§G§G§B§B` **先做 12 位 lookahead 校验再收集**，校验失败当普通文本、**不吞掉后续 12 字符**；③ **HTML 与 ANSI 两条路径**共用一个解析器（网页用 HTML，终端用 ANSI）；④ `§k` 乱码用 rAF 复现，随机字符分 1px/5px 两组**保持每帧等宽**（否则整行抖动）；⑤ **浅色主题另配一套色值**（原版深蓝在浅色面板上不可读） |
| **依赖** | 无（但若已有 P1-3，应同时补测试） |
| **成本** | 1 天 |
| **风险** | 低。**唯一必须注意**：若用 `dangerouslySetInnerHTML`，必须保证转换器负责转义（OPanel 的 `escapeXML` 模式），且**用户可控文本（玩家名/聊天）不能直接进 innerHTML** |
| **验收** | ① MOTD 正确显示颜色/加粗/斜体；② `§x` 十六进制颜色正确；③ 非法 `§x` 序列不吞字符；④ 深浅主题都可读 |

## P1-6 控制台体验补强（终端补全之外的部分）

| 项 | 内容 |
|---|---|
| **问题** | 控制台缺：日志级别过滤开关、文本搜索、字号/换行设置。当前只有固定着色的滚动列表 |

| **成本** | 1 天 |
| **风险** | 低 |

## P2-1 浏览器 WebSocket 双向通道（收益最大的单项）

| 项 | 内容 |
|---|---|
| **问题** | 现在只有 SSE 单向（`web/src/lib/sse.ts:50`）。后果：① **终端补全做不了**（每次按键一条 HTTP，且有后发先至的竞态）；② 高频交互做不了；③ SSE 只写 `data:` 不写 `id:`（`panel/api.js:128-135`）→ **无 `Last-Event-ID`、无回放，断线期间事件永久丢失** |
| **收益** | 解锁交互式控制台与一批实时功能；把「每次操作一条 HTTP」的往返消掉 |
| **参照** | OPanel `BaseEndpoint` / `TerminalEndpoint`（adoption-plan §2.1） |
| **做法** | ① 报文信封 `{type, data}`；**但 BlockNexus 的 agent 通道已有成熟的 `id` + promise map + 超时（`panel/agentlink.js:449-468`），浏览器侧应对齐这套而不是另起一套**；② 按功能分端点 + **类型常量按方向分区注释**（`/* server packet */` / `/* client packet */`，零成本协议文档）；③ 连接参数走 query（如回放条数）、路径参数定位实体；④ **连接时回放一段历史**——把现在的 `GET .../console?tail=300`（`console-panel.tsx:104-106`）合并进 `init` 帧；⑤ **慢消费者治理**：限出站帧数 + 检测写阻塞 + 主动断开（OPanel 用 1024 帧 + `WritePendingException` + close 1013；Node 侧对应 `ws` 的 `bufferedAmount` 检查 + `terminate()`）——**这是进程内 WS 广播必备三件事，否则一个卡住的客户端就是内存放大器** |
| **依赖** | **P1-2（类型契约）**——硬依赖 |
| **成本** | 4–5 天 |
| **风险** | **高**。三点：① **SSE 自带浏览器重连，WS 必须自己写**——这是净增成本，别低估；② 协议一旦上线就难改，所以必须先在 P1-2 把它们类型化；③ 迁移期要同时支持两条通道或一次性切换 |
| **验收** | ① 所有现有 SSE 事件类型都有 WS 等价物且前端无功能回退；② 断线自动重连 + 明确的「连接已断开」提示；③ 有慢消费者保护（人为卡住一个客户端，服务端内存不涨）；④ 控制台历史在连接时回放 |
| **反面清单（必读）** | **不要照抄 OPanel 的 `WebSocketClient`**：它每次 `subscribe` 给同一 socket 挂一个**新的、无法取消的** `message` 监听器（N 个订阅者每条报文 `JSON.parse` N 次；effect 重跑导致同报文处理两次、toast 弹两次）；**零重连**（`onClose` 只有 `console.log`）；**零心跳**（所以连断了都感知不到——这是「没有重连」的上游原因）；`send` 不查 `readyState` 不缓冲；`onError` 把「服务端 error 报文」与「传输层 Event」塞进同一个 `any`。**必须改成**：内部 `Map<type, Set<callback>>` + 单监听器分发、`subscribe` 返回 `unsubscribe`、发送前查 `readyState` 并排队、指数退避重连 + 心跳 + `visibilitychange`/`online` 触发 |

| **收益** | 表达力（`0 4 * * 1` 这类）；消除同步 IO 尖峰 |
| **参照** | OPanel `ScheduledTaskManager`（adoption-plan §2.3） |
| **做法** | ① 引入 **UNIX 5 段 cron** 解析；② **核心机制**：算出下次执行时刻 → 投递一次性定时 → 回调里再算下一次（**不要用固定周期**，否则跨大间隔的 cron 无法表达）；③ **续期基准取 `max(now, next)`** 防时钟回拨重复执行；④ **每个任务一个身份对象**，调度前/执行前都校验「我还是当前任务吗」（**防「任务改了 cron 或删了之后，旧的已排程回调继续跑并给自己重排」这个最经典的竞态**）；⑤ 明确语义：**任务耗时超过间隔时下一次顺延，不补跑**；⑥ **`enabled=false` 的任务仍排程**，只在回调里跳过——这样能保留「下次执行时间」的语义供 UI 展示 |
| **依赖** | 无（但 P2-5/P2-6 依赖它） |
| **成本** | 2–3 天 |
| **风险** | 中。**关键约束：Agent 是零依赖单文件，cron 解析器要么自己写（不复杂，5 段），要么把依赖内联进 `agent/build.js` 的打包器**——这需要在 P2-4 开始前先决策 |
| **必须保留的现有优点** | 调度**全在 Agent 侧**（面板关了照跑，`README.md:300`）。**换成 cron 时不要把这个性质做丢——不要在面板侧加调度器** |
| **验收** | ① `0 4 * * 1` 正确触发；② 改 cron 后旧回调不再触发；③ 删除任务后无残留定时器；④ 面板关闭后任务照跑；⑤ 现有 daily/interval 配置能平滑迁移（或明确**不迁移**、给出用户通告） |

## P3-2 gamerule 与更完整的配置元数据

| 项 | 内容 |
|---|---|
| **问题** | 已有 `PROP_DEFS`（62 键、分组、中文说明、枚举选项、`hint`，`web/src/lib/properties.ts:20-166`），但**无 gamerule 元数据**，只能靠控制台手敲指令 |
| **参照** | OPanel `lib/server-config/presets.ts` + `lib/gamerules/presets.ts`（adoption-plan §3.1(b)） |
| **必须吸取的架构经验** | **表单 schema 要从「服务端真实返回的数据」动态生成，而不是从 preset 生成。** OPanel 的 `generateFormSchema(properties)` 循环的是**真实字段集**，preset 只描述「怎么展示」。这样游戏新增属性时即使 preset 没补说明，**表单也照常渲染**；某个版本删掉的属性也不会凭空出现。反过来若从 preset 生成，就会永久陷入「游戏更新字段 → 面板表单漏了/多了」 |

| **版本分流** | OPanel 为 gamerule 的世代更替（1.21.11 起 snake_case vs 旧 camelCase，59 vs 61 条，改名/新增/删除交织）维护**两份静态数组**而非「一份 + 映射表」——因为差异是双向的，映射表要处理「目标不存在」反而更复杂。选择逻辑集中在**一处** semver 比较 |
| **依赖** | 无 |
| **成本** | 2 天 |
| **风险** | 低。纯前端 + 一个读接口 |
| **验收** | ① gamerule 可视化编辑且保存生效；② 新增/未知规则仍能渲染（有输入控件、无说明）；③ 改动后提示需重启 |

## P3-3 国际化（i18n）

| 项 | 内容 |
|---|---|
| **问题** | **完全没有**。68/122 个 `.ts/.tsx` 含硬编码中文，`pages/` 7/7；`<html lang="zh-CN">` 硬写 |

| **成本** | 4–6 天 |

## P4-2 NBT 读写（注意架构根本限制）

| 项 | 内容 |
|---|---|
| **必须先纠正的误解** | **OPanel 的 `lib/nbt/` 不是二进制 NBT 读取器**——它只处理服务端传来的 SNBT 字符串（Java 侧证据：`record OPanelItemStack(..., String snbt)`）。真正的 NBT 读写发生在 Java 侧的游戏 API 内部 |
| **对 BlockNexus 的含义** | Agent 是**零依赖 JS，没有 MC 服务端 API**。因此：**二进制 NBT（`level.dat` / `playerdata/*.dat` / `region/*.mca`）需要在 Agent 侧从零实现**（格式不复杂，是实打实的工作量）；而**物品/背包编辑在 Agent 侧几乎不可行**——没有游戏内 API，只能改存档文件，且服务器运行时改会与内存冲突。**这是 BlockNexus「远端 Agent 改文件」与 OPanel「跑在游戏进程内」的根本差异，不要硬追** |
| **若只做 SNBT 侧** | 可抄：**按版本分流的解析器工厂**（`compare(version, "1.20.5")` 决定用 Components 还是 Tag 模型）+ **抽象基类把「物品要回答哪些问题」固定下来**，两个实现各自逐字段回答，**防御性解析集中在基类构造器**（解析异常即退化空对象）。这比散落各处的 `if (version)` 好维护得多 |
| **成本** | 只读 NBT：3–5 天；SNBT 渲染：2 天；物品编辑：**不建议** |
| **风险** | 高（写 NBT 有损坏存档的风险，必须只读优先 + 强制备份） |

## P4-3 扩展系统

| 项 | 内容 |
|---|---|
| **参照** | OPanel 把第三方代码约束在四个可控面（adoption-plan §3.2）：独立可发布 API 模块、受限 ClassLoader、事件白名单、显式注册的路由 |
| **Node 侧的最大落差** | **Node 没有 ClassLoader 隔离。** 必须明确承认「Node 插件无法真正沙箱化」，靠**权限模型 + 独立进程**，而不是加载器隔离 |
| **仍然可搬的设计** | ① 独立 npm 包作契约面 + 版本独立演进；② **事件白名单 + 加载期签名校验**（参数类型不在白名单的处理器**在加载期就被拒绝**，而不是运行时静默不触发）；③ **卸载秩序**：停收 → **等待在途派发结束** → 调 `unload()` → 作废 API 句柄 → 释放资源。**这个顺序在任何异步插件系统里都成立**，也是插件系统最容易做错、最容易导致资源泄漏的地方；④ 扩展页面 URL 必须校验（必须以 `/` 开头、不以 `//` 开头、不含 `\`、URI 不绝对、无 authority）——**防止扩展把相对 URL 变成外部跳转**；⑤ **一个可运行的 `example-extension` 比十页文档有用** |
| **成本** | 独立评估（15+ 天） |
| **风险** | 高。安全边界难以在 Node 中真正建立 |
| **建议** | 除非有明确的第三方扩展需求，**暂缓**。优先把内部模块边界划清（P1-2 的类型契约就是第一步） |

# 4. 贯穿全程的纪律

这些不是工作项，而是**每次改动都要遵守的约束**。违反它们的代价通常延迟数周才显现。

### 4.1 版本与发版纪律

| 改动类型 | 要做的事 |
|---|---|
| 改 `agent/src/**` | **必须** `npm run build:agent`，**必须**递增 `agent/src/config.js` 的 `AGENT_VERSION`（面板靠它触发远端自动更新），否则测试会拦下（`test-bundle-fresh.js`） |
| 改面板行为 | 递增 `package.json` 的 `version` |
| 只改面板/前端 | **不动** `AGENT_VERSION` |
| 想要用户拿到更新 | **必须** `gh release create`——用户面板的更新检查只认 GitHub Release 标签，**推送代码不发版** |

### 4.2 不能碰的兼容锚点

- **`panel/crypto.js:25-31` 的 HKDF info 标签 `'mcpan/a2p'`/`'mcpan/p2a'`/`'mcpan/proof'`**：改名会让所有存量 Agent 与新面板握手失败。文件里已有明确注释。**等哪天统一弃用旧 Agent 再换。**
- **`agent/build.js` 的模块 id 与打包格式**：`test-bundle-fresh.js` 逐字节比对产物，改格式要同步改测试。
- **`AGENT_VERSION` 字面量的存在性**：面板用正则从产物文本提取它（`panel/api.js:26-32`），`test-bundle-fresh.js` 第 5 条专门守护这个正则。**改产物结构时不要把它包进无法被正则命中的形式。**

### 4.3 零依赖约束（Agent 侧）

`agent/agent.js` 必须是**零依赖单文件**——这是整条部署链路的前提：SSH 只上传一个文件、systemd `ExecStart=/usr/bin/env node {DIR}/agent.js`、面板 `/agent.js` 匿名下载、README 的手动 `curl` 安装。`test-bundle-fresh.js` 第 4 条断言产物里所有 `require` 都是标准库或相对路径。

**因此：Agent 侧引入任何第三方库都必须先内联进 `agent/build.js` 的打包器**（P2-4 的 cron 解析器、P4-1 的 Anvil 解析都撞这条）。**这是 Agent 侧一切技术选型的第一约束。**

### 4.4 模块清单单一事实源的教训

OPanel 用 `platform-modules.json` 作为**唯一模块事实源**，被三处消费（构建 include、前端构建目标、CI 矩阵）且各自校验，新增一个游戏版本 = 加一条 JSON + 建一个目录。**BlockNexus 的对应痛点是「MC↔NeoForge 前缀映射表有两份重复拷贝」**（`panel/api.js:1082-1089` 与 `agent/src/catalog.js:53-75`）——这是同一类问题的雏形。**建议在 P1/P2 期间把这类的重复常量收敛到单一来源**（Agent 侧可通过打包器注入，或由面板在 `hi` 握手时下发）。

### 4.5 文档纪律

按 `AGENTS.md`：**README 是面向用户的主文档，新功能要在对应章节补一段并更新「API 一览」**。P0 的 `--trust-proxy`/`--secure-cookies` 就需要补。这条容易漏，建议并入每个工作项的验收标准。

**如果只能做三件事**：P0 全部 → P1-3 前端测试 → P1-2 类型契约。这三件做完，后面所有工作都会明显变快。

## A.1 本路线图**有意不覆盖**的项

这些缺口是**真实存在**的，但我建议**暂不排期**，理由如下——需要你判断是否同意：

| 缺口 | 为何暂不排期 |
|---|---|
| **多用户 / RBAC / 权限模型** | 这是**产品定位问题而不是技术问题**。BlockNexus 现在是「个人管理员的自托管工具」，加多用户意味着用户表、会话模型、权限矩阵、审计日志一整套，会显著改变产品形态。**建议等你明确「要不要做成团队协作工具」再决定** |
| **API Token / SSO / MFA** | 同上门槛：都是多用户体系的下游能力 |
| **审计日志** | 单用户场景价值有限；若做多用户则变成必做项 |
| **事件版本协商 / 协议压缩** | 在 P2-1 定协议时**顺手设计**（加个 `v` 字段），但**不做完整协商机制**——面板与 Agent 是同步发版的 |
| **上传并行分块 / 客户端哈希 / tus** | 现有串行 + 断点续传已在生产可用且复杂度高（512KB 分块 + 磁盘指纹 + Agent 重启续传）。**优化收益 < 引入回归的风险** |
| **下载 Range 支持** | 仅对「大文件断点下载」有价值，而现有 SFTP 旁路已绕过 200MB 上限。优先级低 |
| **版本 ↔ Java 兼容性矩阵** | **Agent 刻意不做版本硬拦截**（`lifecycle.js:83-84` 注释：选错版本让服务端自己报错）。这是**有意的设计选择**，改成矩阵反而是过度约束。可考虑只做「建议提示」而非「硬校验」 |
| **数据包 / 配方 / 进度管理** | 需求不明。`initial-enabled-packs` 两个文本键已能应付基本场景 |
| **跨实例 / 跨服务器计划任务、任务依赖编排** | 现有「调度粒度到实例」已覆盖绝大多数场景。跨实例编排是「工作流引擎」范畴，**过重** |
| **容器化 / 正式代码签名 / 异地备份** | 都是**分发与运维**层面的选择，取决于你的发布策略。签名需要购买证书；容器化与「本地 WebView2 外壳」的产品形态冲突；异地备份应先明确存储目标（S3？WebDAV？） |
| **前端状态管理库（Redux/Zustand）** | **建议不引入**。当前规模（7 个页面）用「组件内 state + P1-1 的设置仓库 + SSE/WS 事件」已够。引入状态库会在没有测试的情况下增加抽象成本。**等 P1-3 有测试后，若发现确实需要再评估** |
| **RTL 支持** | 只有阿拉伯语/希伯来语需要。若 P3-3 的目标语言不含 RTL 语言，则零成本跳过 |
